## Contribution

Risk framing first, because it drives every tooling decision below: `role-coercion-proxy` sits inside a trusted internal pipeline (`Claude Code → adapter → Bifrost → vLLM`), not on the public internet. It is a solo-operator, single-crate Rust binary, and deployment/infrastructure/CI-CD automation are explicitly out of scope (confirmed twice — Intent Capture Q6, Scope Document Out of Scope). That combination — memory-safe language, small trust-adjacent (not untrusted-internet) attack surface, no infra to secure — argues for a **lean, code-level security posture**: mechanically enforce the correctness/no-panic requirements the scope document already states, do lightweight dependency hygiene, and explicitly decline the heavier tooling (dedicated SAST, DAST, container/IaC scanning) that has no attack surface to attach to here.

### Lint/format

`cargo fmt --check` and `cargo clippy -D warnings` (already stated in the scope document and the lead's draft) are the right floor and I have no changes to propose there. I'd go one step further: the scope document makes "no `unwrap()`/`panic!()` on the request path" a **Must-Have correctness requirement**, but nothing in the draft turns that into a mechanically-enforced gate — today it can only be caught by manual review or by a test that happens to exercise the panicking path. Clippy can enforce it directly: `#![deny(clippy::unwrap_used, clippy::expect_used, clippy::panic, clippy::indexing_slicing, clippy::unimplemented, clippy::todo)]`, scoped at minimum to the request-handling modules (`main.rs`'s handler, `transform.rs`). This converts a review-dependent requirement into a build-breaking one at effectively zero cost, and it is a Code Style / lint concern, not a deployment concern — it belongs regardless of how the Deployment section resolves.

### SAST

I do not think a dedicated SAST tool (Semgrep, SonarQube, CodeGuru) is warranted for this project. The vulnerability classes those tools earn their keep on — injection, XSS, auth bypass, buffer/memory corruption — are largely either not present in this system's shape (no DB queries, no rendered output, no auth surface described) or already structurally prevented by Rust's memory safety. `cargo clippy -D warnings` plus the additional lint-deny list above gets most of the realistic value a general-purpose SAST scanner would add here, at a fraction of the setup/maintenance cost, and doesn't require standing up any pipeline infrastructure that's out of scope.

One specific SAST-adjacent recommendation tied to this project's actual design, not a generic checklist item: the scope document names **zero-copy JSON handling as the primary design constraint**. If the `transform.rs` implementation can stay entirely in safe Rust (serde's borrowed-data / `Cow` patterns are sufficient for the zero-copy goal), the crate should adopt `#![forbid(unsafe_code)]` at the root — cheap, and it converts "no memory-safety bugs" from a code-review hope into a compiler guarantee. If zero-copy performance instead requires `unsafe` blocks, that unsafe code becomes, by a wide margin, the single highest-priority manual-review target in the whole codebase (it is where Rust's safety guarantees stop applying), and should be flagged as such rather than treated as ordinary code. Which path this takes isn't decided by this stage, but the team should know now that it's the one place a heavier review standard may apply later.

### DAST

Not applicable, and not just because deployment is out of scope — DAST tests a *running* application, and there is no environment in this workflow's scope for one to run against. I'd note for the record (not as an action for this workflow) that if/when a future workflow adds deployment, traditional web-app DAST (OWASP ZAP) is a poor match for this system's actual risk surface (there's no browser-facing content, auth flow, or session state to attack) — **structure-aware fuzzing of `transform.rs`** (`cargo-fuzz` or extending the already-planned proptest/quickcheck property tests with a fuzz corpus) would find far more real bugs, since that module is the one place in the system parsing externally-shaped, potentially-malformed JSON. This is not a gap in the current scope — property-based testing is already planned — just a note that the highest-value dynamic-testing investment for *this* system is fuzzing the parser, not a black-box HTTP scanner.

### Dependency / supply-chain scanning

`cargo-audit` (RUSTSEC advisory scanning against `Cargo.lock`) is warranted and proportionate, and I'd treat it differently from the deployment-related tooling: it's a dependency-hygiene practice that runs against the crate's own lockfile, not infrastructure or a deployment pipeline, so the "deployment out of scope" carve-out doesn't reach it. An internal-only, low-traffic proxy is still exposed to RUSTSEC advisories through the crates it will realistically depend on for this design (an async HTTP framework, `tokio`, `serde`/`serde_json`, an SSE/streaming crate) — that dependency surface is unrelated to whether the binary is ever deployed by this workflow. I'd recommend `cargo audit` as a required local check before merge (it needs no CI to run — a single command any contributor, including a solo operator, runs before each PR) and, separately, flag for the interview whether the team wants the fuller `cargo-deny` (advisory + license policy + source/registry pinning) or just `cargo-audit`'s advisory-only scope — for a solo internal tool with no stated license-compliance driver, I'd default to `cargo-audit` alone unless the team wants the extra `cargo-deny` ceremony.

I'd also note: `Cargo.lock` should be committed for this binary (not `.gitignore`d) — that's what makes `cargo audit` and reproducible builds possible, and it's worth stating explicitly since it's easy for a solo contributor to reach for a library-style `.gitignore` template that excludes it.

SBOM generation (Syft/`cargo-cyclonedx`) — I'd flag this as **not warranted** here. SBOMs earn their value from a compliance or third-party-distribution driver (a customer or auditor needs supply-chain evidence); nothing in the ideation artifacts surfaces a compliance framework in scope for this internal tool, so I'd treat SBOM generation as unnecessary ceremony unless the interview surfaces a reason I'm missing.

### Secret scanning

Proportionate here is light-touch, and for a structural reason, not just because CI is out of scope: the scope document's env-var-only configuration surface (`LISTEN_ADDR`, `VLLM_BASE_URL`, `NOTICE_PREFIX`, `LOG_LEVEL`) has no field that is itself obviously a credential, so the "no hardcoded credentials" requirement is largely satisfied by the configuration *design* rather than needing a scanning tool to catch violations of it. I would not recommend standing up a secret-scanning pipeline (gitleaks/truffleHog in CI) — there's no CI in scope to host it in, and the risk surface it protects against is currently small. Two lightweight, no-infra-required recommendations instead: (1) make sure a local `.env` file (which a developer will likely create for convenience, per the env-var config design) is `.gitignore`d from the very first commit; (2) a `gitleaks` pre-commit hook is cheap enough (no CI required, runs locally via `pre-commit` or a plain git hook) that I'd offer it as an easy yes at the interview rather than push for it as mandatory.

One real gap I want flagged rather than silently assumed away: **the scope document never states whether this proxy authenticates to `VLLM_BASE_URL`.** If the upstream vLLM deployment requires a bearer token or API key, that credential has to come from somewhere — either forwarded from the inbound request's `Authorization` header, or a separately configured secret. The "env-var configuration, no hardcoded credentials" requirement implies a credential path exists but the artifacts don't say which shape it takes. This matters for secret handling (an env-var-sourced upstream token still needs "don't log it" and "don't echo it in error bodies" discipline) and I'd raise it as an interview question rather than assume either shape.

### Deployment section

I agree with the lead's flag: the Deployment section should read **"not applicable — deployment is out of scope for this workflow"** rather than carrying `org.md`'s deploy-on-merge/staging default forward. From a DevSecOps angle specifically: every deploy-time security control that section's default implies — DAST against staging, container/image scanning, IaC scanning, a production approval gate — has no artifact to attach to when no deployment pipeline is being built. Leaving the org default in place risks a downstream stage inferring that a CI/CD pipeline (and the deploy-time gates that ride on it) is implied work, which contradicts the twice-confirmed out-of-scope declaration.

One clarification I'd want stated alongside that reword, so it isn't misread as "no security gates at all": marking Deployment not-applicable removes only the *deploy-time* gates. The *build-time* gates I recommend above (`clippy` deny-lints, `cargo fmt --check`, `cargo audit`, the existing test suite) belong under Testing Posture / Code Style, not Deployment, and remain fully in scope regardless of how this section resolves.

That surfaces one enforcement question the draft doesn't address: with CI/CD automation explicitly out of scope, how do the quality gates actually get enforced — purely manually by the solo operator before each merge, or is a minimal test-only CI workflow (run `cargo test`/`clippy`/`fmt`/`audit` on push, with no deploy step) considered in-scope "project tooling" rather than "deployment infrastructure"? I'd flag this for the interview: it changes whether `cargo audit` and the clippy deny-lints are self-enforcing or rely on discipline alone.
